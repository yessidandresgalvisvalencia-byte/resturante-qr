# Temporary cloud vault bridge
Founder decision: use the existing independent GRUKStorage MongoDB cluster temporarily while acquiring customers; own hardware is deferred. No paid resources, Google Drive or production data operations are authorized by this code.
The provisional adapter uses a separate database gruk_storage_vault, collections archives, archive_chunks and vault_quota. Signed encrypted archives only, 256 KiB chunks, conservative 32 MiB aggregate accounting cap (not actual cluster free space). Atomic publication and quota reservation require a replica-set transaction. No deletion or overwrite API. The cap is an internal design choice, not proof of available Atlas quota. No second independent copy is claimed.
Before enabling: verify keyring contract, real synthetic transaction and retrieval on disposable replica, measured cluster capacity, provision dedicated least-privilege vault identity and collections, verify connectivity and restore, approve any real backup separately. Existing catalog worker is not authorized for these collections. Do not change operational databases or runtime release guards. Migration to independent persistent infrastructure remains required for full disaster recovery.

## Provisioning boundary
In the existing GRUKStorage Atlas project, create only database gruk_storage_vault and collections archives, archive_chunks and vault_quota. Initialize vault_quota with {_id:"enterprise",used:0} only on a verified empty vault; never reset an existing counter. Create a dedicated custom role with find/insert on archives and archive_chunks, find/update on vault_quota; no delete, no administration or access to operational databases. Restrict gruk_vault_worker to the GRUKStorage cluster. Keep the URI in a secret GRUK_VAULT_MONGO_URI, not a variable or chat. The expected host is a nonsecret variable GRUK_VAULT_EXPECTED_HOST. The new probe is read-only and explicitly enabled, verifies quota and collection reads, not write permissions. Actual provisioning and network allowlisting require authorized Atlas access. Synthetic transaction and AGE recovery passed at 501f7dda787e5fa5d5ace1a72b909d852ffdc17b, run 45894097861 job 140163603872.

Write permission probe: GRUK_VAULT_WRITE_PROBE_ENABLED=true and GRUK_NATIVE_REAL_BACKUP_ENABLED=false are mandatory. The probe inserts unique synthetic markers and increments quota inside an explicitly aborted transaction; never commits and checks marker absence afterward. Run only after authorized provisioning and network access; no production backup approval is implied. Actual Atlas write authorization remains unverified.

## Controlled hosted verification
After reviewed merge, provisioning, and temporary narrowly scoped network authorization, set repository variable GRUK_VAULT_PROBE_ALLOWED=true only for the authorized verification window. Run the dedicated GRUK Vault controlled verification workflow on main with vault_probe=read or write_abort. Default none skips the vault job; the existing inspection workflow stays secret-free. Set the variable false again and remove temporary network authorization afterward. The workflow never enables real backups, never commits the synthetic transaction and never uploads artifacts. Do not use a broad network allowlist. If a narrow network path is unavailable, stop. The workflow is not an operational backup scheduler. Previous connection and abort-probe tests passed in run 45894596093; actual Atlas permissions remain unverified.

## Phase 2 readiness gate
The source preflight requires a separate `gruk_enterprise_backup_reader` Atlas user with exactly `read` on `restaurante`, the explicit source hostname, distinct vault hostname and TLS. It checks authenticated roles and dbStats and the internal vault quota without reading business documents or writing data. It never enables backups. Its size estimate is conservative screening only; verify actual Atlas physical space and exact encrypted archive size independently. The manual workflow defaults to disabled and requires narrow network access, secrets and explicit authorization. Real backup remains blocked until durable recovery keys, capacity, network, isolated restore and separate approval are verified. Never reuse operational credentials.
